# 集客のノウハウと実験記録

このサイトの裏の目標は、Web サービスを作ったあとに「広める方法」を試し、他のサービスでも使える手順として確立すること。施策は実験として扱い、うまくいったものもいかなかったものも、ここに残す。

- 書き方: 実験ごとに「仮説、やったこと、基準値、測る日、結果、学び」を書く。結果が出たら「学び」を下の「確立した手順」に移す。
- 数値の出どころ: Search Console（以下 GSC）と GA4 は、ブラウザで画面を開いて読む（analytics-mcp は接続できないことがある）。
- 関係する文書: `doc/marketing-strategy.md`（当初の戦略）、Beads `qr_code_create-36h`（2026-11-10 の検討と判断待ち）

## 1. 確立した手順（他のサービスでも最初にやること）

結果が出て、効果を確かめたものだけをここに書く。

1. **公開したら、GSC に登録したサイトマップの URL が正規の URL と一致しているか確認する。**
   - www の有無、http と https の違いに注意する。正規の URL と違うと、リダイレクトのため一度読まれたきりで、その後は更新されない。
   - 確認する場所: GSC の「サイトマップ」画面で、「最終読み込み日時」が最近か、「検出されたページ数」が実際の URL 数と合っているかを見る。
   - 事例（E1）: 4 月に送った www 付きのサイトマップは 2026-04-17 に 1 度読まれたきりで、検出は 28 ページだった。正規 URL の版を送り直すと、すぐに 42 ページと検出された。インデックスへの効果は E1 の結果で確かめる。
2. **流入の割合で判断するときは、期間と母数を先に確かめる。**
   - 事例: 2026-10-22 の分析では「流入の約 45% が ChatGPT 経由」とされ、AI 検索への対策を優先する根拠になった。90 日・283 セッションで見直すと、GA4 の AI Assistant は 4%（10 セッション）だった。母数が数十のときの割合は、数件の訪問で大きく動く。
   - 手順: GA4 では「過去 90 日」で、セッション数そのものも書き添える。月に 100 セッションを切る段階では、割合より件数で話す。
3. **施策を始める前に、GSC で「インデックスされていない」のか「順位が低い」のかを切り分ける。**
   - 事例: 訪問者が少ない原因を、当初は露出や記事の不足と考えていた。GSC を見ると、sitemap の 42 URL のうちインデックス登録は 12 で、ツール本体の /create と海外版はどれも未登録だった。記事を足しても、インデックスされなければ届かない。
   - 手順: 「ページ」画面の登録済みの件数を、sitemap の URL 数と比べる。差が大きければ、記事を書くより先にインデックスの問題を直す。

## 5. 開発の進め方で得た学び（集客の施策を実装するとき）
- 記事の文言を変える施策は、`npm run build` のあとに `npm test` を流す。ビルド成果物を検査するテスト（staticOutput）は、成果物がないと飛ばされる。E4 ではテストを先に流したため、更新日の不一致を見逃し、E5a で見つけて直した。
- 記事に更新日（updated）を足すと、sitemap の lastmod、article:modified_time、BlogPosting の dateModified が変わる。古い日付を固定した既存テストが落ちるので、同じ作業で直す。
- 用語は画面の表記に合わせる。文章の検査（yomiyasu）が語を嫌っても、言い換えると画面と食い違う。E5a では「解像度」を `.yomiyasu-words/allow.txt` で許可した。

## 6. やらないと決めたこと
- 票や「はてなブックマーク」を頼んで集める、同じ文面を複数のコミュニティに一斉に投稿する（規約違反やスパム扱いの危険がある）
- 「追跡なし」とうたう（このサイトは GA4 を使っている。正しくは「入力した URL をサーバーに送らない」）
- プレスリリースの有料配信（個人開発のツール単体では効果が小さいと見込んだ。2026-11-10 時点の判断）
