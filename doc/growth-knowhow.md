# 集客のノウハウと実験記録

このサイトの裏の目標は、Web サービスを作ったあとに「広める方法」を試し、他のサービスでも使える手順として確立すること。施策は実験として扱い、うまくいったものもいかなかったものも、ここに残す。

- 書き方: 実験ごとに「仮説、やったこと、基準値、測る日、結果、学び」を書く。結果が出たら「学び」を下の「確立した手順」に移す。
- 数値の出どころ: Search Console（以下 GSC）と GA4 は、ブラウザで画面を開いて読む（analytics-mcp は接続できないことがある）。
- 関係する文書: `doc/marketing-strategy.md`（当初の戦略）、Beads `qr_code_create-36h`（2026-11-10 の検討と判断待ち）

## 1. 確立した手順（他のサービスでも最初にやること）

結果が出て、効果を確かめたものだけをここに書く。

1. **公開したら、GSC に登録したサイトマップの URL が正規の URL と一致しているか確認する。**
   - www の有無、http と https の違いに注意する。正規の URL と違うと、リダイレクトのため一度読まれたきりで、その後は更新されない。
   - 確認する場所: GSC の「サイトマップ」画面で、「最終読み込み日時」が最近か、「検出されたページ数」が実際の URL 数と合っているかを見る。
   - 事例（E1）: 4 月に送った www 付きのサイトマップは 2026-04-17 に 1 度読まれたきりで、検出は 28 ページだった。正規 URL の版を送り直すと、すぐに 42 ページと検出された。インデックスの登録済みは、送り直しから 2 週間で 12 件から 24 件に増えた（E1）。
2. **流入の割合で判断するときは、期間と母数を先に確かめる。**
   - 事例: 2026-10-22 の分析では「流入の約 45% が ChatGPT 経由」とされ、AI 検索への対策を優先する根拠になった。90 日・283 セッションで見直すと、GA4 の AI Assistant は 4%（10 セッション）だった。母数が数十のときの割合は、数件の訪問で大きく動く。
   - 手順: GA4 では「過去 90 日」で、セッション数そのものも書き添える。月に 100 セッションを切る段階では、割合より件数で話す。
3. **施策を始める前に、GSC で「インデックスされていない」のか「順位が低い」のかを切り分ける。**
   - 事例: 訪問者が少ない原因を、当初は露出や記事の不足と考えていた。GSC を見ると、sitemap の 42 URL のうちインデックス登録は 12 で、ツール本体の /create と海外版はどれも未登録だった。記事を足しても、インデックスされなければ届かない。
   - 手順: 「ページ」画面の登録済みの件数を、sitemap の URL 数と比べる。差が大きければ、記事を書くより先にインデックスの問題を直す。

### E1: 正規 URL のサイトマップを送り直す
- 仮説: GSC に登録したサイトマップが www 付きの URL だったため、4 月 17 日以降は読み込まれていない。新しいページ（use-cases の追加分、ブログ、海外版）が見つかりにくく、インデックスが 12 件で止まっている。正規 URL のサイトマップを送れば、登録が増える。
- やったこと: 2026-11-10 に GSC の「サイトマップ」画面から `https://qr-create.jp/sitemap.xml` を送信した。送信の直後に「成功しました」となり、42 ページが検出された（旧版は 28 ページ）。旧版の www 付きサイトマップは消していない。
- 基準値: インデックス登録済み 12 / 42
- 測る項目: GSC の「ページ」画面の登録済みの件数、サイトマップ画面の最終読み込み日時
- 結果（2026-11-18、送信から 8 日後）
  - サイトマップ画面: 正規 URL のサイトマップは最終読み込み 2026-11-18、検出 43 ページ（年賀状の記事が増えた分を含む）。www 付きの旧版は 2026-04-17 のまま
  - 「ページ」画面: 登録済み 12 → 22、未登録 24 → 39。未登録の内訳は、リダイレクト 16（変化なし）、検出 - インデックス未登録 15（新しく出た区分）、クロール済み - インデックス未登録 6、重複 2
  - 評価: 効果あり（暫定）。登録済みが 8 日で約 2 倍になった。「検出 - インデックス未登録」が 15 件出たのは、サイトマップから URL を新しく知ったが、まだクロールしていない状態とみられる。2 回目（11-24）で、この 15 件が登録済みに移るかを見る
- 結果（2026-11-24、送信から 14 日後）
  - サイトマップ画面: 正規 URL のサイトマップは最終読み込み 2026-11-23、検出 43 ページ。www 付きの旧版は 2026-04-17 のまま
  - 「ページ」画面: 登録済み 22 → 24、未登録 39 → 38。未登録の内訳は、リダイレクト 16、検出 - インデックス未登録 15、クロール済み - インデックス未登録 6 → 5、重複 2
  - 注意: 「ページ」画面の最終更新日は 2026-11-16 だった。この画面の件数は 8 日前までの集計で、11-17 以降の動きは入っていない。同じ日に URL 検査で見た /pt-br は登録済みだったので、実際の登録はこの件数より進んでいる
  - 評価: 効果あり。登録済みは基準値の 12 から 24 へ、2 週間で 2 倍になった。ただし増えたのは最初の 1 週間（12 → 22）にほぼ集まり、そのあとは 2 件だけだった。「検出 - インデックス未登録」の 15 件は、画面の集計では動いていない
- 学び
  - サイトマップの URL の誤りを直すと、1 週間ほどで登録がまとまって動く。確立した手順 1 の裏づけになった
  - サイトマップを直しても、全部は登録されない。2 週間たっても 43 URL のうち 15 件ほどが「検出 - インデックス未登録」に残る。ここから先は、サイトマップではなく、ページの中身や内部リンクの問題として扱う
  - GSC の「ページ」画面は集計が 1 週間ほど遅れることがある。件数を読むときは、右上の最終更新日も書き添える。個別のページの今の状態は URL 検査で見る

### E2: インデックス登録のリクエスト（対照群あり）
- 仮説: サイトマップだけでなく URL 検査から登録をリクエストすると、インデックスに入るのが早くなる。
- やったこと: 2026-11-10 にリクエストした。
  - 実験群（リクエストした）: /create、/en、/en/create
  - 対照群（リクエストしていない）: /es、/pt-br、/de、/es/create、/pt-br/create、/de/create
  - いずれも当日の状態は「検出 - インデックス未登録」
  - 注意: 実験群は、日本語のツール本体と英語版で、ページの性質が対照群と違う。結果は参考にとどめる
- 測る項目: URL 検査の状態（登録済みかどうか）、GSC の「前回のクロール」の日付
- 結果（2026-11-18、リクエストから 8 日後。URL 検査で 1 件ずつ確認）
  - 実験群: /create、/en、/en/create の 3 件とも「URL は Google に登録されています」
  - 対照群: /es と /de は登録済み、/pt-br は未登録（「検出 - インデックス未登録」）
  - 評価: 差は見えなかった。リクエストしなかったページも、同じ期間にほとんど登録された。E1 のサイトマップの送り直しと同時に始めたので、登録が進んだ主な理由はサイトマップ側とみられる
- 学び（暫定）: インデックス登録のリクエストは、サイトマップが正しく読まれている状態では、1 週間の単位では効果が見えにくい。手間は小さいので、新しい記事を出した直後の 1 回（E7 で実施）には使ってよいが、頼りにしない。2 回目（11-24）で /pt-br が登録されるかを見る
- 結果（2026-11-24、リクエストから 14 日後。URL 検査で確認）
  - 実験群（3 件）: 1 回目で 3 件とも登録済み。2 回目は見直していない
  - 対照群（6 件）: /es、/pt-br、/de の 3 件は登録済み（/pt-br は 1 回目のあとに登録された）。/es/create、/pt-br/create、/de/create の 3 件は未登録
    - /pt-br/create と /de/create は「検出 - インデックス未登録」。前回のクロールは「該当なし」で、まだ一度もクロールされていない
    - /es/create は「URL が Google に認識されていません」で、参照元サイトマップも「検出されませんでした」と出た。本番の sitemap.xml には載っている（同じ日に確認）。1 回目の記録は /es だけで、/es/create は見ていなかった
  - 評価: 言語のトップ同士（/en と /es・/pt-br・/de）では、リクエストの有無による差は 2 週間でなくなった。作成ページでは差が出た。リクエストした /en/create は 8 日以内に登録され、リクエストしていない 3 言語の作成ページは 14 日たってもクロールされていない。ただし英語版と他の言語版という違いが重なっているので、リクエストの効果だとは言い切れない
- 学び
  - トップのように内部リンクが集まるページは、リクエストしなくても 1〜2 週間で登録される
  - 作成ページのように、内容が他の言語版とほぼ同じで文章の少ないページは、サイトマップに載せるだけではクロールが後回しになる。こういうページはリクエストする意味がありそうで、次に同じ場面があればリクエストして確かめる
  - 1 回目に対照群の一部しか見ていなかったため、作成ページの差に気づくのが 1 週間遅れた。対照群は毎回すべて見る
- 追試（2026-11-28、ユーザーの承認のうえ実施）: 未登録の 3 件（/es/create、/pt-br/create、/de/create）にインデックス登録をリクエストした。3 件とも「インデックス登録をリクエスト済み」と出た
  - リクエストの前の状態: 3 件とも「検出 - インデックス未登録」（/es/create は 11-24 の「URL が Google に認識されていません」から変わり、サイトマップと参照元ページが出ていた）。サイトマップに載せてから 18 日たっても、クロールされていなかった
  - 同じ日の「ページ」画面: 登録済み 30、未登録 32（最終更新日 2026-11-23）
  - 見る日: 2026-12-05。8 日以内に登録されれば、/en/create（リクエストから 8 日以内に登録）と同じ動きで、「文章の少ないページはリクエストが効く」の裏づけになる
- 測り方の注意: URL 検査の入力欄は、前の URL の文字が残ったり履歴の候補が Enter を受けたりして、別の URL の結果のまま画面が変わらないことがある。結果を読むときは、画面上部に出る URL が調べたいものかを必ず確かめる

### E4: CTR の低いページの title と description を直す
- 仮説: /use-cases/poster は平均掲載順位 7.0 で 1 ページ目に出ているのに、CTR が 0.5%（表示 208、クリック 1）しかない。use-cases の 9 本が同じ型の title（「〇〇用QRコードの作り方と活用方法」）で、検索結果で中身が伝わっていない。中身が一目で分かる文にすれば CTR が上がる。
- やったこと（Beads qr_code_create-b8y、dev 225f7e1）
  - title: 「ポスター用QRコードの作り方と活用方法」→「ポスター用QRコードの大きさと距離の目安、効果の測り方」
  - description: 読み取り距離別のサイズ表、掲示場所ごとの計測、A4 に 4 枚並べる印刷用 PDF の 3 点を約束する文に変えた。3 点とも本文にある内容
  - 本文は事実を変えずに書式だけ整え、更新日 2026-11-10 を付けた
- 基準値: 表示 208、クリック 1、CTR 0.5%、平均掲載順位 7.0（2026-08-08〜11-07）
- 測る項目: GSC の検索パフォーマンスで、ページを /use-cases/poster に絞った CTR と掲載順位。比べる期間は、本番反映の前の 4 週間と後の 4 週間。順位が大きく動いたときは、CTR の変化を title の効果とは言い切らない

- 本番反映: 2026-11-10（main c9089dc）。本番で title、article:modified_time、sitemap の lastmod が 2026-11-10 になったことを確認した

### E5: 引用されやすい形に記事を直す
- 仮説: 定義文、表、手順、よくある質問のある記事は、検索の強調スニペットや AI の回答に引用されやすい。着地の多い 2 本を直せば、表示回数と AI 経由の流入が増える。

## 5. 開発の進め方で得た学び（集客の施策を実装するとき）
- 記事の文言を変える施策は、`npm run build` のあとに `npm test` を流す。ビルド成果物を検査するテスト（staticOutput）は、成果物がないと飛ばされる。E4 ではテストを先に流したため、更新日の不一致を見逃し、E5a で見つけて直した。
- 記事に更新日（updated）を足すと、sitemap の lastmod、article:modified_time、BlogPosting の dateModified が変わる。古い日付を固定した既存テストが落ちるので、同じ作業で直す。
- 記事の見た目は、本番の画面を人が見て初めて気づく崩れがある。2026-11-15 にユーザーが、ガイドの表に枠線がないことを見つけた（ガイドの CSS にだけ表の規則がなく、ほかの記事の線も白背景に対して 1.4:1 と薄かった）。記事を足すときは、表・長い URL・コードがスマートフォン幅でどう見えるかを E2E で確かめる。記事を描く CSS に表の規則があることは静的テストで、枠線の色と 390px のはみ出しは E2E で検査するようにした（qr_code_create-ttm）。
- 用語は画面の表記に合わせる。文章の検査（yomiyasu）が語を嫌っても、言い換えると画面と食い違う。E5a では「解像度」を `.yomiyasu-words/allow.txt` で許可した。
